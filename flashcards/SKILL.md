# /flashcards — Multiple-choice quiz from your notes

Operates relative to the **current working directory** (a course/learning-path folder containing a `CLAUDE.md` with a Progress section and chapter note files). All cache/history storage lives under `<cwd>/.flashcards/`.

## Step 0: Optional per-repo config

If `<cwd>/.flashcards-config.json` exists, read it. Currently supported key:
- `resultsDir` — where Step 5 writes the per-session results file, relative to cwd. Defaults to `.flashcards/results/` when the config file or this key is absent.

This is how a repo opts into a visible, non-dot-prefixed results archive (e.g. `exam-prep/flashcards/`) without the skill itself hardcoding any repo-specific directory name — same pattern as `learning-recap`'s per-repo config for course/meeting-title matching. Don't invent other hardcoded paths for other repos; if a new per-repo behavior is needed, add it as a new config key here, not as a special case in the step logic.

## Step 1: Parse arguments

Arguments can appear in any order/combination, all optional:
- **scope** — a course name or chapter name (substring match, case-insensitive) against the course directories / chapter files listed in the Progress section of `CLAUDE.md`. If omitted → scope is everything currently marked completed across all courses.
- **count** — an integer, how many questions to ask this session. Default **10**. If the scoped question pool has fewer than `count` questions, ask what's available and say so.
- **mode** — `new`, `clear`, or `import <path>`:
  - `new` (optionally scoped): regenerate cached cards for the chapters in scope only. Delete just those chapters' cache files before regenerating.
  - `clear` (never scoped — always global): deletes the entire `.flashcards/` directory, including history. **This is destructive and cannot be undone (loses all quiz history/weak-spot data)** — confirm with the user before deleting. If confirmed, delete and stop (no quiz runs after a clear).
  - `import <path>` (never scoped by course/chapter argument — scope is discovered from the file's content instead): ingest missed questions from an external mock exam (a text file or PDF export from a site like CyberSkill, ExamPro, etc. — not generated by this skill). Skips the quiz entirely this run; see **Step 3b** below instead of Steps 3-6.
- **`--include-gaps`** (flag, off by default, combinable with any mode): also treat `gap-topics/**/*.md` notes under cwd (this repo's convention for material a mock exam tested that the official course notes don't cover — see that repo's `exam-prep/CLAUDE.md` if present) as part of the pool. Off by default because gap topics are, by definition, outside the scope of the actual certification exam — quizzing and weak-spot tracking should default to exam-scoped material only, and gap topics should only enter the wrong-rate signal when the user deliberately opts in to gauging that extra knowledge. If no `gap-topics/` directory exists under cwd, this flag is a no-op. Applies to:
  - **quiz mode**: gap-topic notes are added to Step 2's chapter pool, tagged `course: "Coverage gap"` and `chapter: <gap-topic subdirectory name>`.
  - **`import <path>` mode**: Step 3b's topic-matching also checks gap-topic notes, so a miss that only maps to a gap topic gets seeded into history instead of falling through to the coverage-gaps bucket.

## Step 2: Resolve scope to chapter files

Read `CLAUDE.md` in cwd, specifically the `## Progress` section, to get the list of completed chapters and their file paths per course. Filter this list by the scope argument if given. If nothing matches, tell the user and stop.

If `--include-gaps` was passed, also find every `gap-topics/**/*.md` note under cwd and add each as its own pool entry with `course = "Coverage gap"` and `chapter = <the gap-topic subdirectory name>` (e.g. `structured-data-extraction`), filtered by the scope argument the same way as course chapters.

## Step 3: Ensure cards are cached for each chapter in scope

Cache layout:
```
.flashcards/
  cards/<course-slug>/<chapter-slug>.json
  history.jsonl
  weak-spots.md
  study-guides/<import-source-slug>-<date>.md
```

For each chapter file in scope:
- If its cache JSON exists and mode isn't `new`, reuse it — do not regenerate.
- Otherwise, read the chapter note (summary + user's notes/insights) and generate a question bank directly (you are the question generator — no external call needed). Aim for 6-10 questions per chapter covering distinct topics from that chapter, each with exactly 4 options and one correct answer. Write the cache file as:

```json
{
  "course": "Introduction to agent skills",
  "chapter": "What are Skills",
  "generated": "<today's date>",
  "questions": [
    {
      "id": "q1",
      "topic": "short topic tag, e.g. 'skill frontmatter'",
      "question": "...",
      "options": ["...", "...", "...", "..."],
      "answer_index": 0
    }
  ]
}
```

Use kebab-case slugs for course/chapter directory and file names.

## Step 3b: Import missed questions from an external exam (`import <path>` mode only)

This mode exists because self-generated quiz history only tells you what *this skill* thinks you're weak on — it can't see how you actually did on a real practice exam. Importing closes that gap: real misses become real weak-spot weighting and a real study guide, grounded in your own notes.

1. **Read the file.** Text or PDF (PDF: read all pages, batching per the Read tool's page-range limit if it's long). Formats vary a lot between exam sites — be liberal about what counts as a question record. At minimum, expect either:
   - a **trio**: question text, the answer given, and the correct answer, or
   - a **pair**: question text, the answer given, and a right/wrong verdict (no correct-answer text shown).

   If a record's status can't be determined at all (no verdict, no correct answer, nothing to indicate pass/fail), skip it and note it in the final report rather than guessing. If the file looks like a **full result set** (all questions, not just the missed ones) rather than a missed-only export, don't assume every record is a miss — only import records that are explicitly marked wrong/incorrect. If you can't tell whether the file is missed-only or a full set, ask the user before importing anything, rather than silently treating correct answers as misses (or vice versa).

2. **Match each missed question to a topic.** Build the same chapter/topic pool this skill already uses for quizzing (all cached chapters in scope, or generate cache entries per Step 3 first if none exist yet — a topic match needs *something* to match against). If `--include-gaps` was passed, this pool also includes existing `gap-topics/**/*.md` notes (per Step 2). For each missed question, decide which chapter/topic it's actually about based on subject matter, not surface wording. Reuse an existing `topic` tag from the cached cards when there's a clear match — don't invent a near-duplicate tag for the same concept. Only create a new short kebab-case topic tag when the material genuinely isn't one of the existing ones.

3. **Flag coverage gaps.** If a missed question doesn't map to *any* existing chapter/topic in the active pool (course chapters, plus gap-topics notes if `--include-gaps` was passed) — the notes simply don't cover that material — don't force a match. Collect these separately and call them out in the final report; this is a real signal (a course gap, or content the notes never captured), not a bug in the matching. Without `--include-gaps`, a miss that matches an *existing* gap-topics note still falls through to this bucket rather than silently matching — the report in step 7 should say so explicitly (e.g. "N of these coverage gaps already have a gap-topics note — rerun with `--include-gaps` to track them"), so the user knows the flag would resolve them instead of assuming they're wholly unstudied.

4. **Seed history.** Append one line to `.flashcards/history.jsonl` per successfully-matched missed question:
   `{"date":"YYYY-MM-DD","course":"...","chapter":"...","question_id":null,"topic":"...","correct":false,"source":"import:<file-basename>","imported_question":"<original question text, trimmed>"}`
   The `source` and `imported_question` fields distinguish imported misses from self-generated quiz attempts and keep the original wording auditable, since imported questions don't have a cached `question_id` the way generated cards do.

5. **Regenerate weak-spots.** Rebuild `.flashcards/weak-spots.md` from the full history exactly as in Step 6, so the import is reflected immediately — don't wait for a quiz run.

6. **Write the study guide.** For every topic touched by this import, pull the relevant chapter note(s) (summary + insights) and write `.flashcards/study-guides/<file-basename>-<today's date>.md`: highest-impact/most-missed topics first, core theory explained in exam-relevant terms (definitions, how it works, when it applies), explicit X-vs-Y contrasts where the source material invites confusion, a suggested study order, and 1-2 short self-check questions per major topic. Mark clearly, per topic, whether it's grounded in an actual missed question from this import or in general chapter weak-spot history — don't blur the two. List any coverage gaps from step 3 in their own section at the end, since those can't be studied from existing notes alone.

7. **Report and offer next step.** Tell the user: how many questions were imported, how many mapped to existing topics vs. got a new tag, and how many were coverage gaps (with the actual question text for those, since there's no note to point to). Point to the study guide file. Then ask whether they want to immediately run a quiz scoped to just the topics touched by this import (i.e. re-invoke this skill with those topics as scope) — don't launch it automatically, since they may want to read the study guide first.

Formats from new exam sites will keep surprising this step — if parsing goes wrong or a site's export shape doesn't fit the trio/pair assumption above, treat that as a sign this step needs updating, not a reason to force a bad match.

## Step 4: Build the question pool and pick questions

Combine all questions from the in-scope cache files into one pool.

Read `.flashcards/history.jsonl` if it exists (one JSON object per line: `date`, `course`, `chapter`, `question_id`, `topic`, `correct`, plus optional `source`/`imported_question` on lines seeded by Step 2b's import mode). Compute a wrong-rate per `topic` (wrong answers / total attempts for that topic; topics never attempted count as highest priority, i.e. unknown = treat as weakest). Weight question selection toward higher wrong-rate topics, but still sample across the whole scope rather than hammering one chapter — don't let a single weak chapter crowd out the rest of the requested count.

Pick `min(count, pool size)` questions. If truncating the pool, mention how many questions exist in total.

## Step 5: Run the quiz

For each picked question, use the AskUserQuestion tool: single-select, the 4 options as choices (shuffle option order so the correct answer isn't always in the same position), header = the chapter or topic tag (kept ≤12 chars for the UI).

Immediately after each answer, teach — don't just verdict. This is the whole point of the quiz; a bare "right/wrong, matches a known pattern" comment doesn't help the user actually understand the material. For **every** question, right or wrong:
1. State right/wrong.
2. Give a real explanation grounded in the chapter note: what the correct concept actually is, why it's correct, and — if the user picked wrong — specifically why their chosen option's reasoning fails (not just "that's the wrong pattern"). 2-4 sentences. If the user picked a distractor that represents a known reflexive-but-wrong default (e.g. from an exam-analysis note), name that pattern *in addition to* the concept explanation, not instead of it.
3. Append a line to `.flashcards/history.jsonl`: `{"date":"YYYY-MM-DD","course":"...","chapter":"...","question_id":"q1","topic":"...","correct":true|false}`
4. Record the question, options, the user's answer, the correct answer, and the teaching explanation from step 2 in memory (in scratchpad notes, not a file yet) — Step 6 compiles all of these into the results file.

Do this per-question (not batched at the end) so progress is saved even if the user stops mid-quiz.

## Step 6: Wrap up

After all picked questions are answered:
- Report the score (`X/N`) and list which topics/chapters had wrong answers this session.
- Regenerate `.flashcards/weak-spots.md` from the **full** history.jsonl: a markdown table of topics sorted by wrong-rate descending (topic, course/chapter, attempts, wrong, wrong-rate%), so future sessions and the user can see where to focus.
- Write a results file compiling every question's teaching explanation from Step 5 (not just the wrong ones), so the session's teaching content survives as a study artifact rather than scrolling out of the conversation:
  - Path: `<resultsDir>/flashcards-results-<YYYY-MM-DD-HHmm>.md`, where `resultsDir` is the value from Step 0's config (defaults to `.flashcards/results/` if no config file/key was found).
  - Content: session score up top, then one section per question in the order asked — question text, options, the user's answer, the correct answer, and the full teaching explanation from Step 5. End with a "Weakest topics this session" list pulled from the chapters/topics that had wrong answers.
  - No approval gate — write the file directly, don't ask the user to confirm its contents first.
